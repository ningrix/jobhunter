# 17 - 差距分析：算法 / 架构 / 产品力 / 商业化（对照 FRESUME + 自查）

> 2026-09-06。只列真实问题，每条带代码证据。结论先行：**JobHunter 当前的"算法"是加权词面统计，"Agent 投递"只有 Mock 驱动，"商业化"为零。三个支柱各有一个 must-fix 的空洞。**

## 一、算法：我们有一个"分数"，没有一个"算法"

| # | 缺口 | 证据 | FRESUME 对照 |
|---|------|------|--------------|
| 1.1 | **匹配分 = 规则统计，不是智能**。五维权重（skills 0.4/experience 0.25/education 0.15/city 0.1/salary 0.1）全是字面命中、年限求和、学历查表、阈值比较。LLM 不参与打分 | `match-scorer.ts`（纯规则，无 AI 调用）；LLM 只在 tailor/greeting 出现 | 岗位匹配全链路 LLM：深读 JD → 逐段重写 → 生成匹配证据与风险，分数只是外壳，内核是语义理解 |
| 1.2 | **语义检索是死代码**。`embeddings` 表（schema.ts:264）+ provider `embed()` 方法存在，但全项目 **0 读 0 写** | grep 实证：无任何业务代码 insert/from embeddings | 其"知识库"喂进每条改写建议的依据 |
| 1.3 | **零学习闭环**。建议的接受/拒绝、投递结果（通过/未通过）、面试反馈都不回流；匹配权重靠用户手动拖滑杆 | matchWeights 为 profile 手调 JSON；无任何模型/规则随行为更新 | 主库+知识库持续沉淀，画像随使用变准 |
| 1.4 | **无数据资产**。职位来源 = mock + 手动导入 + 雷达抓公开页（NEEDS_VERIFICATION） | job-sources 实测能力 | 秋招信息流每日更新（运营资产）+ 大厂库 + 用户主库 |

**判定：1.1+1.2 是同一个洞——匹配的真实性。** 产品宣称"智能匹配"，实际是关键词计数器。这是最危险的差距，因为它是首页主打的数字。

## 二、架构：三处"生产不可用"

| # | 缺口 | 证据 |
|---|------|------|
| 2.1 | **任务模型是轮询**：前端 `waitForTask` 30s 超时轮询 ai-tasks；无 SSE 流式。长任务（整份简历重写、批量匹配）体验 = 转圈 | `lib/client.ts:35`；对照 FRESUME 全链路 SSE + 段落级 delta |
| 2.2 | **SQLite + 本地文件 = 单机玩具**。无法多实例部署，无队列/worker，对象存储缺失；PostgreSQL 是"生产目标"非现实 | drizzle sqlite 驱动；`/api/v1/files/{id}` 读本地盘 |
| 2.3 | **真实投递能力缺席**：agent drivers 目录只有 `mock-driver.ts`。"半自动投递"差异化目前是架构 + 测试，不是能力 | `src/server/agent/drivers/` 仅 mock |
| 2.4 | **AI 成本与可观测为零**：无 token 计量、无按用户核算、无缓存去重、无 prompt 版本管理 | 全局 grep 无 usage 统计落库 |

**判定：2.1/2.2 决定"能不能上线给真人用"，2.4 决定"敢不敢收费"。**

## 三、产品力：我们不回答用户的第一个问题

1. **缺冷启动场景**。求职者打开产品的第一个问题是"我该投什么方向？"——FRESUME 用岗位方向推荐（教育背景→方向+薪资范围）+ 秋招信息流 + 大厂聚合页回答了。JobHunter 假设用户已有简历、已有职位来源，**入口是空的**。
2. **无主库**。基本信息在简历里、投递偏好在 profile、打招呼语事实在 resumeFacts——同一份"我"存了三遍，改一处不变全身（FRESUME profile-source 单点投影全部产物）。
3. **无可带走的交付物**。我们的输出停在网页打印 PDF；FRESUME 每次使用产出 docx 适配简历、面试指南、网申包——用户"带着东西离开"，这才是传播的载体。
4. **交互形态低半档**：表单+预览 vs 画布+区域对话+版本树。此项最不重要，放最后。

## 四、商业化：为零，且有现成答卷

- 现状：无账号分层、无配额、无支付、无订单、无增长机制。
- FRESUME 已验证的**零支付集成**打法：收款码 + "付款后私信开通"人工审核 + 订单后台 + 体验额度 + `trial_quota_exceeded` 错误码即营销位 + 邀请码。全套一天可抄完。
- 定价锚点已被市场验证：¥1 当天 / ¥9.9 周 / ¥19.9 月，5 类计数（对话/上传/生成/匹配/分析对话）。
- 我们的可付费点排序：**适配简历生成（刚需高频）> AI 对话额度 > 批量匹配**。安全投递是差异化但难收费（责任重）。
- **需要用户拍板的定位冲突**：仓库已开源（目的=给面试官看）。商业化路径三选一：① open-core（核心开源 + 配额/网申包等 Pro 闭源）② 双仓库（开源演示版 + 商业版）③ 开源版免费但内置配额系统（宣传"开箱即用的商业化脚手架"本身也是卖点）。

## 五、主攻建议（排序 = 依赖关系 + 单位改动收益）

1. **激活语义匹配（真算法）**：复用用户已配的国产模型 embedding API（智谱/Qwen 均有），职位+简历向量化写入已有的 `embeddings` 死表；匹配分 = 规则分与语义分加权混合；溯源 UI 刚好展示"语义依据"。改动集中、基建已存在、可全量测试。
2. **AI 任务流式化（真架构）**：ai-tasks 轮询 → SSE 进度流（meta/段落 delta/阶段事件），对齐已逆向的 FRESUME 协议。
3. **商业化最小闭环（真商业）**：配额表 + 免费额度 + 三档定价 + 人工开通后台 + 错误码营销位 + 欢迎信。零支付集成。
4. **主库 profile-source（产品力地基）**：网申包、打招呼语、简历模板全部改为投影。
5. 后置：docx 导出、PG 迁移、真实浏览器驱动（受安全红线约束，需单独评估）。

**一句话：先让"智能匹配"名副其实（1），再让它能上线服务真人（2），然后开始收钱（3）——1/2/3 正好构成"产品→架构→商业"的完整补强环。**
