# 22 - V4.1 排序引擎：可解释、可评估的混合匹配

> 依据 [V4 路线图定稿](20-V4-路线图定稿.md)：**不扩产品面**——不加新页面、不加新业务功能，只把「岗位匹配」的内核换真。
> `Match Score = w1·语义相似 + w2·规则分 + w3·LLM Judge`，语义层默认关闭，关闭时行为与 V4.0.1 逐位一致（向后兼容）。

## 1. 交付内容

### 1.1 激活语义层（embeddings 死表 → 0 读 0 写 → 语义索引）

- 迁移 0008：`user_profiles.semantic_match_enabled`（默认 false）+ `user_profiles.hybrid_weights`（json）+ `job_matches.hybrid_scores`（json 明细）；
- `server/ai/embedding-service.ts`：`chunkResumeContent` / `chunkJobForEmbedding`（段落级 chunk，≤12 块 × 400 字）+ `embedOwnerChunks`（缓存键 = owner + embed 模型，chunk 文本即内容指纹，变更自动重嵌、陈旧清理）；
- `gateway.embedText` / `getEmbedModel`：向量调用统一入口，计量落 `ai_usage_logs`（scene=embed，与 runAI 同口径）；Provider 接口新增 `embedModel` 标识；
- 复用已有基建：`AIProvider.embed?`（Mock 确定性 64 维哈希向量 / OpenAI 兼容 `/embeddings`）与 `embeddings` 表结构 V4.0 前已建好，本阶段零结构变更激活。

### 1.2 混合排序内核

- `server/core/hybrid-ranking.ts`（纯函数，零 IO）：`cosineSimilarity`、`semanticScore`（每个职位 chunk 取简历最佳命中对 → 均值 → 0-100，同时产出证据）、`normalizeHybridWeights`（缺省/非法/全 0 回落默认 0.4/0.3/0.3）、`hybridTotal`、`ndcg`、`spearman`；
- 新任务类型 `match_semantic`（runner）：向量 → 相似度 → Judge → 回写 `totalScore`（混合分）+ `hybridScores`（子分/权重/语义命中段落证据/Judge 理由）+ `aiExplanation`（Judge 产出，兼容 MatchExplanation）+ `summary`；进度经 TaskProgressContext 双通道（落库 + SSE）；
- `computeMatch` 分支：`semanticMatchEnabled=true` → 入队 match_semantic（规则分先落库占位，任务失败保留规则分）；否则原行为逐位不变。

### 1.3 LLM Judge

- 新场景 `match_judge`（prompts.ts）：输入规则分 + 语义相似证据 + 简历/职位，输出 `{score, summary, strengths, gaps, risks, reasons}`——score 供混合，reasons 逐条给分依据供溯源，解读四件套直接复用现有展示；
- Mock 确定性实现：`score = 0.5·规则分 + 0.2·技能维度 + 0.3·语义分`（对两输入单调，评测集可精确回归）。

### 1.4 可解释（复用 V3.4 溯源思路）

- 规则证据：`dimensionScores` + `reasons`（原有）；
- 语义证据：`hybridScores.semantic.evidence[]`——职位 chunk × 简历 chunk 最佳命中对 + 相似度；
- Judge 证据：`hybridScores.judge.reasons[]` 逐条给分依据；
- 职位中心匹配弹窗展示「混合匹配 X 分（语义 · 规则 · Judge）」，语义任务全程进度可见，失败显式降级回规则分。

### 1.5 可评估（排序质量第一次可回归）

`ranking-eval.test.ts`：4 份种子简历 × 6 个种子 JD 的 gold set（0-3 等级），全链路确定性（规则纯函数 + Mock 确定性向量 + 确定性 Judge），实测：

| 指标 | 纯规则 | 混合（默认权重） |
|---|---|---|
| NDCG（4 简历均值） | 0.991 | **0.996** |
| Spearman vs gold | — | 0.847（均值） |

断言：规则 NDCG ≥ 0.9；**混合 ≥ 纯规则**（混合排序不允许更差）；Spearman ≥ 0.7。评测数值打印保留在输出中，回归失败可定位到具体简历。

### 1.6 开关与权重（UI 在 AI 设置页，数据在 profile）

- 设置页新增「语义匹配引擎」卡片：开关 + 三权重滑杆（0-1 步进 0.05，显示原始值，生效时按三者之和归一化）；
- 数据走 `PATCH /users/me/profile`（`semanticMatchEnabled` / `hybridWeights`）——与 `matchWeights` 同走 profile，mock 用户（未配 Key）也可开启用于演示；
- 语义关闭时一切照旧：现有 305+ 测试零改动通过即为兼容性证明。

## 2. 关键决策

1. **混合总分回写 `totalScore`**：推荐五桶/阈值（STRONG 85 / RECOMMENDED 70）与全部排序 UI 以 `totalScore` 为唯一事实源，混合分直接回写即全链路生效；规则五维分保持 `dimensionScores` 原样（不被污染，可对照）。
2. **开关数据放 profile 而非 ai_settings**：语义层是匹配行为偏好（与 matchWeights 同类）；且 ai_settings 行以 API Key 密文为 NOT NULL 必填，未配 Key 的 mock 演示用户无法建行——放 profile 让演示模式也能开语义层（mock 向量确定性、零成本）。docs/20 只约束「开关在用户 AI 设置页」，满足。
3. **chunk 即指纹**：embeddings 表 `chunk` 列存原文，内容变更 → 指纹不命中 → 重嵌；换 embed 模型 → 模型名不匹配 → 各自独立缓存，互不污染。
4. **Judge 输入含语义证据**：评估官能看到「语义相似度 + 最佳命中段落」，把语义信号纳入 Judge 理由链，形成单一可解释叙事。

## 3. 已知边界（如实记录）

1. **Mock 向量是词面级信号**（3-gram 哈希分桶）：mock 模式下的语义分反映词面重合，不是真语义；真实国产 embedding 模型（智谱 embedding / Qwen text-embedding）的效果 **NEEDS_VERIFICATION**（需用户配 Key 后实测）。
2. **价格表**：embedding 价格沿用 pricing 表 `text-embedding` 前缀（¥0.07/1M，NEEDS_VERIFICATION），mock 免费；真实调用计量口径与 chat 一致。
3. **单机余弦是暴力扫描**：embeddings 按 owner 索引取出全量 chunk 两两计算——当前数据量（单用户简历×职位 ≤ 数百 chunk）无压力；规模化时升级 pgvector / 近似检索（接口不变）。
4. **语义任务失败不静默**：embed API 挂掉 → 任务 failed → 前端显式提示「已保留规则分」，总分保持规则分（不产出假混合分）。
5. **评测集是词面友好的 gold set**：NDCG 0.99 的高分反映种子集构造，不代表真实分布表现；随真实使用可扩充 gold set（这正是把评测放进 vitest 的意义）。
