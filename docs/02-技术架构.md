# 02 技术架构

## 1. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Next.js 15 (App Router) + React 19 + TypeScript + Tailwind CSS 4 | 服务端布局鉴权 + 客户端数据拉取 |
| API | Next.js Route Handlers（`/api/v1/*`） | 统一 `defineRoute` 包装器：鉴权 → Zod 校验 → 业务 → 错误映射 |
| ORM | Drizzle ORM + better-sqlite3 | 零外部依赖、Windows 友好；schema 分层设计可迁移 PostgreSQL |
| 鉴权 | jose (HS256 JWT, 15min) + 随机刷新令牌（仅存 sha256 哈希，30 天，轮换 + 吊销） | httpOnly Cookie，兼容 `Authorization: Bearer` |
| 校验 | Zod | 前后端共享 schema（`src/shared/schemas.ts`） |
| AI | 自研网关层：Mock Provider / OpenAI 兼容 Provider | GLM / DeepSeek / Qwen 均提供 OpenAI 兼容接口，配置即切换 |
| 异步任务 | ai_tasks 表 + 进程内执行器（接口与 BullMQ 一致，生产可替换 Worker 进程） | 任务状态机 queued→running→succeeded/failed |
| 测试 | Vitest（55 用例） | 直接调用 route handler，免起服务 |

## 2. 系统分层

```
┌─────────────────────────────────────────────────────┐
│ 前端页面 (app)/dashboard|resumes|jobs|applications   │
│   → src/lib/client.ts 统一 fetch（信封解析+任务轮询）│
├─────────────────────────────────────────────────────┤
│ API 路由层 app/api/v1/**（薄控制器）                 │
│   defineRoute: 鉴权 → Zod → 业务编排 → 错误映射     │
├─────────────────────────────────────────────────────┤
│ 领域服务层 server/core/*-service.ts                  │
│   auth / user / resume / job / match / application  │
│   / reminder / dashboard（所有权校验、状态机、聚合） │
├──────────────────────────────┬──────────────────────┤
│ AI 编排层 server/ai/runner   │ AI 网关 server/ai/   │
│   任务队列+状态机+各类型处理器 │   gateway: 限额→重试 │
│   （调用 gateway 并持久化）   │   →JSON解析→用量计量 │
├──────────────────────────────┴──────────────────────┤
│ 基础设施 db/client (SQLite+WAL, 自动迁移) · lib/auth │
└─────────────────────────────────────────────────────┘
```

依赖规则：路由层只做校验与编排 → core 领域服务 → db/ai 基础设施；**禁止路由层直写 SQL，禁止 core 反向依赖 runner**（runner 可依赖 core 的纯函数）。

## 3. AI 网关设计

- **Provider 抽象**：`AIProvider.chat({scene, prompt, input, json})` + 可选 `embed()`。
  - `mock`（默认）：确定性规则解析器（正则提取薪资/城市/年限/学历/技能词典），离线可用，测试稳定
  - `openai`：OpenAI 兼容 `/chat/completions`（json mode）与 `/embeddings`，60s 超时
- **统一入口 `runAI(scene, input, {userId, taskId})`**：
  1. 限额检查：按用户按自然日统计 `ai_usage_logs`，超限抛 9003/HTTP 429
  2. 调用 Provider（真实 Provider 失败重试 3 次，指数退避）
  3. JSON 解析（剥离代码围栏），失败计入重试
  4. 用量计量落库（含失败记录，scene 标记 `:error`）
- **任务化**：4 类场景（parse_resume / parse_jd / optimize_resume / match_analysis）全部走 `enqueueTask → executeTask` 状态机；处理器负责调用网关并持久化业务结果（回写简历版本/职位结构化/分析报告/匹配解读）。前端经 `GET /ai-tasks/:id` 轮询。
- **安全边界**：前端永不直连模型；Prompt 明令禁止编造经历；AI 生成内容带 source 标记。

## 4. 关键流程时序（上传简历解析）

```
浏览器 → POST /resumes/upload (multipart)
  → 提取文本(txt直读/pdf-parse/mammoth) → 存储原件
  → 建 resume + resume_files(pending) + 空白v1版本
  → enqueueTask(parse_resume) → 202 {resumeId, taskId}
  → 进程内 executeTask：runAI → ResumeContent JSON
      → 回写版本 content(source=upload) + resume_files(done)
浏览器 → GET /ai-tasks/:id 轮询 → succeeded → 刷新详情
```

## 5. 存储与部署

- **本地/MVP**：SQLite（WAL 模式，外键开启），启动时自动执行 `./drizzle` 迁移（幂等）；文件存储 `data/uploads/`
- **生产路径**：`getDb()` 单点封装，切换 PostgreSQL 需替换 driver 与迁移产物；对象存储换 S3/OSS；任务执行器换 BullMQ Worker 进程（接口已对齐）
- 配置全部环境变量化（`.env` / `.env.example`）

## 6. 与原设计的偏差说明

| 原设计 | 实际实现 | 原因 |
|---|---|---|
| pnpm Monorepo（apps/web + apps/worker + packages/*） | 单 Next.js 应用 + 内部分层（server/core、server/ai、db、shared） | MVP 交付速度优先，依赖规则不变，后续可平移拆包 |
| PostgreSQL + pgvector | SQLite + Drizzle | 本环境无 Docker；向量检索以 Mock embed + 规则评分替代，表结构已预留 embeddings |
| Redis + BullMQ | ai_tasks 表 + 进程内异步执行 | 去外部依赖；状态机与轮询接口一致，可直接替换 |
| 邮件提醒 | 站内提醒（邮件通道预留） | MVP 站内已闭环 |
